# Full Application Audit — Yami KMP (Android · iOS · Desktop)

_Generated 2026-06-09 on branch `parity-fixes`. Read-only audit — no source changed by this pass._

## 1. Scope & method

A multi-agent audit fanned out **26 specialized review agents** (all Claude Opus 4.8), one per feature/platform area, each tracing its area end-to-end through the *real* executable code:

> UI (`:ui`) → ViewModel/State/Intent/Effect (`:presentation`) → use case (`:domain`) → repository interface → impl (`:data`, sometimes delegating into `:shared`) → Room DAO / DataStore / Ktor / `:platform` actual / files on disk — opening **all three platform actuals** (`androidMain`/`iosMain`/`desktopMain`) and the DI bindings in `PlatformModule.{android,ios,desktop}.kt`, and comparing every behavior to the `native-app/` reference as ground truth.

Because the codebase carries large stale machine-generated KDoc, **every raw finding was handed to a separate adversarial verifier agent** instructed to refute it against real code (default to *refuted* without hard evidence). Three synthesis agents then produced the repair plan, the readiness checklist, and a completeness critique.

**Run:** 113 agents · ~11.0M agent tokens · ~91 min wall-clock. **Raw findings:** 84 → **74 confirmed/adjusted**, **10 refuted** (false positives, mostly stale-KDoc or native-parity-matches).

**Constraints honored:** no changes to `sources_repositry/`, `native-app/`, or owner WIP files (`ui/.../home/HomeScreen.kt`, `MangaLekRepositoryv2.kt`, `MangaSource.kt`, `.idea/...`); everything local on `parity-fixes`; nothing pushed.

### Headline

**No release-blocking bug survived adversarial verification** — the aggressive skeptic pass downgraded every initially-"blocker" claim. The app is in strong shape: Library, Reader, Details, Downloads, History, Search, Settings, and persistence are faithfully wired on all three targets. What remains is a tight set of **5 high** and **11 medium** real issues (below), a long tail of **58 low** polish/parity items, and — critically — a large **runtime-verification gap**: this is a pure static trace; nothing was confirmed on a device or even through the compile gate. See §6.

### One synthesis-level release gate to call out

The readiness pass flagged the **adult-content gate** as *verify-before-release* (high): confirm no adult content renders before the gate on **every** Details entry point, including the cache-first open. (The specific History-path bypass *claim* was investigated and **refuted** — native is no stricter — but the gate should still be smoke-tested end-to-end since compliance can't ship unverified.)

#### 1. [HIGH] Saving from Home persists the manga with ZERO chapters; native fetches and persists the full chapter list

- **Area / feature:** home — Save/bookmark a manga from the Home feed row
- **Platform(s):** All
- **Type:** missing-feature  |  **Confidence:** high  |  **Verifier verdict:** adjusted
- **Current behavior:** HomeViewModel.onSaveToggle(item) calls toggleInLibrary(item.toManga()) using the use case's default chapters = emptyList(). HomeFeedItem.toManga() (HomeViewModel.kt:317-325) copies only api/language/title/url/coverUrl/rating/genres — no chapters. ToggleInLibraryUseCase.invoke (ToggleInLibraryUseCase.kt:61-74) then calls repository.addToLibrary(manga, chapters=emptyList()), and LibraryRepositoryImpl.addToLibrary (LibraryRepositoryImpl.kt:149-158) calls libraryDeo.saveMangaWithChapters(manga, chapters=emptyList()). Result: the library row is created with no saved_chapters. Chapters are only backfilled later, gated on isInLibrary, when the user opens that manga's Details (DetailsViewModel.kt:577-581 persistNewChapters). Until then the Library card shows 0 total chapters, and a LibraryRefreshWorker run on a Home-only-saved manga would diff the fetched list against an EMPTY saved set, marking every chapter as new and emitting a notification per chapter (notification spam) via persistNewChaptersAndNotify (LibraryRepositoryImpl.kt:191-214).
- **Expected behavior:** Saving from Home should persist the manga together with its chapter list, exactly as native does — so the library entry is immediately complete (chapter counts correct, update-tracking baseline established, no false 'all chapters are new' notification burst).
- **Root cause:** Native HomeRoute.kt:185-198 onSaveToggle, on the ADD branch, performs a network fetch of the full chapter list — chaptersViewModel.getChaptersDataR(mangaItem.url).collect { mangaInfo -> homeViewModel.toggleManga(mangaInfo) } — and native HomeViewModel.toggleManga (HomeViewModel.kt:151-165) saves manga.chapters.toList().toSavedEntities(1).reversed(). The KMP HomeViewModel.onSaveToggle (HomeViewModel.kt:289-302) skips the chapter fetch entirely and passes the empty default. The VM KDoc at HomeViewModel.kt:292-294 even claims 'adding can fetch chapters before persisting' (justifying the in-flight spinner), but the code path never fetches them — the spinner shows for an add that does no network work.
- **Key files:** `presentation/src/commonMain/kotlin/me/manga/yamiapk/presentation/home/HomeViewModel.kt:289-302`; `presentation/src/commonMain/kotlin/me/manga/yamiapk/presentation/home/HomeViewModel.kt:317-325`; `domain/src/commonMain/kotlin/me/manga/yamiapk/domain/usecase/library/ToggleInLibraryUseCase.kt:61-74`; `data/src/commonMain/kotlin/me/manga/yamiapk/data/repository/LibraryRepositoryImpl.kt:149-158`; `native-app/app/src/main/java/me/manga/yami/navigation/routes/HomeRoute.kt:185-198`; `native-app/app/src/main/java/me/manga/yami/presentation/features/home/ui/viewmodel/HomeViewModel.kt:151-165`
- **Native (ground truth):** Native ADD path fetches full chapters then persists them (HomeRoute.kt:191-198 + HomeViewModel.kt:151-165). KMP persists none. Native is ground truth; KMP diverges.
- **Recommended fix:** Before persisting on the ADD branch, fetch the manga's chapter list (the same fetch Details uses — a FetchMangaDetails/chapters use case) and pass the resulting List<Chapter> into toggleInLibrary(manga, chapters). The in-flight savingKeys spinner is already wired and gated on isAdd, so it correctly covers the network round-trip once the fetch is added. Keep the REMOVE branch unchanged (instant DB delete). This mirrors native's getChaptersDataR -> toggleManga(mangaInfo) flow.
- **Fix risk:** Medium — adds a network dependency (a chapter-fetch use case) into HomeViewModel, which previously had none; must reuse the existing source-routed chapter fetch and map AppError on failure (emit ShowError, do not leave savingKeys stuck). Confirm the chosen use case keys on the same (api, url) the source expects.
- **Suggested tests / smoke checks:** Unit test: onSaveToggle(add) issues a chapter fetch and calls toggleInLibrary with the non-empty chapter list; on fetch failure it emits ShowError and clears savingKeys. Integration: a manga added from Home shows correct chapter count in Library and a subsequent LibraryRefresh does NOT notify for pre-existing chapters.
- **Verifier correction:** Platforms: the zero-chapter persistence is All-platforms (commonMain HomeViewModel/UseCase/RepoImpl), but the notification-spam fallout is ANDROID-ONLY — the LibraryRefreshWorker that diffs against the empty saved set lives only in :app (app/.../work/LibraryRefreshWorker.kt); iOS/Desktop have no such worker (domain KDocs label it "Android-only legacy LibraryRefreshWorker"). Root-cause/path: the spam does NOT flow through LibraryRepositoryImpl.persistNewChaptersAndNotify (LibraryRepositoryImpl.kt:191-214) as the finding states — that rework method is only reachable via RefreshAllLibraryChaptersUseCase, which is DI-bound (LibraryReworkModule.kt:145) but invoked by no ViewModel/UI and is currently dead. The live Android spam comes from the legacy :shared-backed worker's own diff at app/.../work/LibraryRefreshWorker.kt:258-276 (newChapters = fetched.filterNot { localChapters.contains(url) }; addNewChapterNotification per chapter), with localChapters empty for a Home-saved manga. Everything else in the finding (missing chapter fetch on add, false VM KDoc at HomeViewModel.kt:292-294, membership-gated Details backfill, native fetches+persists full list) is accurate. Severity stays high (wrong/incomplete persisted data vs native + real Android notification burst); type is wrong-data / missing-feature rather than a pure missing-feature.

#### 2. [HIGH] AVIF images render on Android but fail to decode on iOS/Desktop (Skiko has no libavif), producing broken pages for AVIF-serving sources

- **Area / feature:** image-loading — AVIF-encoded chapter pages / covers — decode on iOS & Desktop
- **Platform(s):** iOS, Desktop
- **Type:** platform-gap  |  **Confidence:** high  |  **Verifier verdict:** adjusted
- **Current behavior:** On iOS/Desktop the singleton ImageLoader registers only HighQualitySkiaImageDecoder (IosImageDecoderRegistry / DesktopImageDecoderRegistry, both registerAll() = listOf(HighQualitySkiaImageDecoder.Factory())). Its decode() calls `Image.makeFromEncoded(bytes)` (HighQualitySkiaImageDecoder.kt:69) OUTSIDE the try/catch (the try starts at line 70). Skiko's bundled Skia has no libavif, so makeFromEncoded throws on AVIF input; the exception propagates out of decode() and Coil surfaces an error state → broken/blank page. The file's own KDoc documents this as a KNOWN LIMITATION (HighQualitySkiaImageDecoder.kt:59-68), affecting both online reads and offline CBZ reads (iOS/Desktop CBZ writers store page bytes verbatim, no transcode).
- **Expected behavior:** AVIF chapter pages and covers that render correctly on Android (and in the native Android app) should also render on iOS and Desktop. Native is Android-only, so 'parity' here means the KMP iOS/Desktop targets should not regress AVIF support for sources Android handles.
- **Root cause:** Android decodes AVIF via the org.aomedia.avif.android JNI decoder registered as AvifDecoderCoil.Factory (AndroidImageDecoderRegistry.kt:17-19; AvifDecoderCoil.kt:35-151). iOS/Desktop have no equivalent: the only registered/fallback decoder is Skia, and Skiko ships without libavif, so Image.makeFromEncoded cannot parse AVIF (HighQualitySkiaImageDecoder.kt:57-69). No iOS/Desktop AVIF Decoder.Factory exists in :platform.
- **Key files:** `platform/src/nonAndroidMain/kotlin/me/manga/yamiapk/platform/image/HighQualitySkiaImageDecoder.kt:57`; `platform/src/iosMain/kotlin/me/manga/yamiapk/platform/image/IosImageDecoderRegistry.kt:16`; `platform/src/desktopMain/kotlin/me/manga/yamiapk/platform/image/DesktopImageDecoderRegistry.kt:16`; `platform/src/androidMain/kotlin/me/manga/yamiapk/platform/image/AndroidImageDecoderRegistry.kt:17`; `platform/src/androidMain/kotlin/me/manga/yamiapk/platform/image/AvifDecoderCoil.kt:35`
- **Native (ground truth):** Native (Android-only) registers AvifDecoderCoil.Factory on its Coil ImageLoader (native-app/.../di/coli/CoilModule.kt: add(AvifDecoderCoil.Factory())), so AVIF decodes at full quality on the original app. The KMP iOS/Desktop targets have no AVIF path — a target-introduced regression.
- **Recommended fix:** Add an iOS AVIF Decoder.Factory routing AVIF bytes through ImageIO/UIImage (system AVIF since iOS 16) and a Desktop AVIF decoder (bundle an AVIF/libavif decode path, e.g. an imageio-avif plugin or a JNI/native lib), then register them ahead of HighQualitySkiaImageDecoder in IosImageDecoderRegistry / DesktopImageDecoderRegistry. As an interim mitigation, move `Image.makeFromEncoded(bytes)` inside the try block in HighQualitySkiaImageDecoder.decode() so an AVIF failure is a clean decode error rather than relying on Coil's outer catch (cosmetically the same broken page but defensively explicit). Both edits are in :platform (allowed).
- **Fix risk:** Medium-to-high — adding real AVIF decode on iOS requires cinterop to ImageIO; Desktop needs a third-party AVIF library on the JVM classpath (none today). The interim try-block move is low risk.
- **Suggested tests / smoke checks:** On iOS sim and Desktop, open a chapter from a source known to serve AVIF pages; pages should decode (not show the error/retry pane). Also open a downloaded chapter (CBZ) of such a source offline. Compare the same source on Android, which decodes AVIF correctly.
- **Verifier correction:** Root cause, affected platforms (iOS + Desktop), and severity (high) are all correct as reported. One factual correction to currentBehavior: the claim "iOS/Desktop CBZ writers store page bytes verbatim, no transcode" is wrong. The iOS/Desktop CBZ writers DO transcode pages to WebP via SkiaWebpEncoder (IosCbzWriter.kt:90, DesktopCbzWriter.kt:97); they store bytes verbatim ONLY for formats Skia cannot decode. For AVIF specifically that fallback IS taken (Skia has no libavif), so the page is written verbatim as .avif (allow-listed in DefaultCbzReader.kt:169) and then fails to render through the same Skia decoder on read-back. So the offline-CBZ AVIF breakage is real, but the mechanism is "AVIF-only verbatim fallback," not "all pages verbatim." Also note: the inline comment at App.kt:346-348 ("iOS/Desktop registries return empty lists") and the audit-trail postscripts in all three ImageDecoderRegistry files (claiming the legacy :shared half is the wired consumer and the :platform flip hasn't landed) are STALE — App.kt now injects the :platform ImageDecoderRegistry interface directly via Koin. The runtime conclusion is unaffected: iOS/Desktop have no AVIF decoder.

- **Recommended fix:** If parity with native monetization is required, port the rewarded-ad download gate into the rework: a presentation-layer coordinator (mirroring AdViewModel) that, on each chapter-download intent, increments a persisted counter and — every Nth — shows a rewarded ad via AdProvider.showRewarded(), proceeding only on AdResult.EarnedReward and blocking (with user feedback) on Dismissed; fall through to proceed on NotLoaded/Failed exactly as native does. If the product decision is 'no ads in the KMP app', record it explicitly as an intentional divergence (it currently reads as an unfinished port, not a decision).

The iOS/Desktop AdProvider actuals are intentional no-op stubs per the facade contract (iOS Free tier serves no ads; Desktop has no first-party JVM AdMob SDK), so they are not parity regressions — there is no native counterpart on those targets. Everything else in the finding is accurate: facade bound, zero consumers, MobileAds.initialize called but never used, rework download path (DetailsViewModel.kt:765) has no ad gate. #### 4. [HIGH] Source base/image URL changes are not propagated to saved manga/chapter/history/notification rows, unlike native

- **Area / feature:** refresh — Source registry refresh (startup remote source-list seed)
- **Platform(s):** All
- **Type:** missing-feature  |  **Confidence:** high  |  **Verifier verdict:** confirmed
- **Current behavior:** SourceRegistryRefreshRepositoryImpl.refreshSources() upserts ONLY the `sources` registry table (baseUrl/baseVersion, imageBaseUrl/imageUrlVersion, siteState, delete) when a newer server version arrives. It never rewrites the per-entity URLs already stored for saved manga. After a source's domain moves server-side, existing in-library manga/chapters/history/notifications keep their old (now-dead) URLs, so opening a saved manga or refreshing its chapters fails until the user removes and re-adds it.
- **Expected behavior:** When baseVersion increases, native calls propagateUrlChanges(api, newBaseUrl) which rewrites manga.url, chapter.url, history.mangaUrl/chapterUrl, and notification.mangaUrl/chapterUrl via replaceBaseUrl(...). When imageUrlVersion increases, native calls propagateImageUrlChanges(api, newImageBaseUrl) rewriting manga/history/notification image URLs. This keeps already-saved content working after a domain change — the entire point of the version-comparison seed.
- **Root cause:** Intentional scope-narrowing in the KMP port, flagged by the impl's own KDoc as 'Deliberate scope narrowing vs native (flagged for review)'. data/src/commonMain/.../repository/SourceRegistryRefreshRepositoryImpl.kt:40-46 documents the omission; the upsert() at lines 104-140 updates only the registry row and never touches the manga/chapter/history/notification DAOs. Native does both: native-app/.../repo_settings/domain/UpdateSourcesRepository.kt:171-172 (propagateUrlChanges before updateBaseUrlAndVersionByName) and :193-194 (propagateImageUrlChanges), with helpers at :238-271 and :272-356.
- **Key files:** `data/src/commonMain/kotlin/me/manga/yamiapk/data/repository/SourceRegistryRefreshRepositoryImpl.kt:40`; `data/src/commonMain/kotlin/me/manga/yamiapk/data/repository/SourceRegistryRefreshRepositoryImpl.kt:104`; `native-app/app/src/main/java/me/manga/yami/presentation/features/repo_settings/domain/UpdateSourcesRepository.kt:171`; `native-app/app/src/main/java/me/manga/yami/presentation/features/repo_settings/domain/UpdateSourcesRepository.kt:238`; `native-app/app/src/main/java/me/manga/yami/presentation/features/repo_settings/domain/UpdateSourcesRepository.kt:272`
- **Native (ground truth):** Native rewrites all per-entity URLs on a version bump (UpdateSourcesRepository.propagateUrlChanges/propagateImageUrlChanges) so saved manga survive a domain move. KMP omits this, so saved manga break after a server-side domain change.
- **Recommended fix:** Add a URL-propagation step to SourceRegistryRefreshRepositoryImpl.upsert(): when src.baseVersion > currentBase, before/with updateBaseUrlAndVersionByName, rewrite the stored URLs for that api across manga/chapter/history/notification (and image URLs on imageUrlVersion bump) using a replaceBaseUrl equivalent. This needs new narrow repository ports + DAO update queries (getMangaByApi/getMangaIdsByApi + per-table url updates) since the rework :domain Source model dropped the routing fields. Mirror native's replaceBaseUrl host-swap semantics exactly.
- **Fix risk:** Medium — touches four additional tables and requires new DAO queries/ports; a wrong replaceBaseUrl could corrupt stored URLs. Should be guarded by tests against native's replaceBaseUrl behavior and only fire on a genuine version bump.
- **Suggested tests / smoke checks:** Unit test the upsert with a higher baseVersion and assert manga/chapter/history/notification URLs are host-swapped; assert no rewrite when version is not newer; assert image URL propagation on imageUrlVersion bump; assert per-source catch keeps other sources upserting.
- **Verifier correction:** Finding confirmed as-is on platforms (All — the gap is in commonMain, not platform-specific), root cause (intentional scope-narrowing, self-flagged in KDoc), and behavior. One scope refinement: the breakage is CONDITIONAL, not unconditional. It triggers only when (a) a source's baseVersion or imageUrlVersion increases server-side (an actual domain/CDN move) AND (b) the user already has saved manga/chapters/history/notifications from that source. Until such an event, persisted URLs remain valid and nothing breaks. Additionally worth noting: the per-entity DAO query+update methods native's propagation depends on (getMangaByApi, getMangaIdsByApi, getChaptersByMangaIdR, getHistoryByApi, getNotificationsByApi) were also removed from the KMP DAOs in the 'Task #388' retire, so restoring parity requires re-adding those DAO methods, not just the repository logic. Severity stays 'high' (silently breaks saved content users rely on) rather than 'blocker' because it is event-conditional, not a guaranteed launch-time failure or unconditional data loss.

#### 5. [HIGH] Server-side base-URL changes are NOT propagated into stored manga/chapter/history/notification URLs (native rewrites them)

- **Area / feature:** sources — Startup source-registry refresh (base-URL / domain migration)
- **Platform(s):** All
- **Type:** wrong-data  |  **Confidence:** high  |  **Verifier verdict:** confirmed
- **Current behavior:** SourceRegistryRefreshRepositoryImpl.upsert() only updates the `sources` registry row (baseUrl/baseVersion via updateBaseUrlAndVersionByName, imageBaseUrl/imageUrlVersion, siteState). When a source's baseVersion bumps server-side (domain moved), the new base URL is written to the registry, but every previously-stored absolute URL on library manga rows, chapter rows, history rows, and notification rows still points at the OLD domain. Listing/home/search fetches recover (BaseManga.getBaseUrl() re-reads the registry baseUrl), but opening a saved/library manga or reading from history calls fetchMangaChaptersF(manga.url)/fetchChapterDataF(chapter.url) with the STALE absolute URL -> the fetch hits the dead domain and fails with no explanation tying it to the domain move.
- **Expected behavior:** On a baseVersion/imageUrlVersion bump, rewrite the stored absolute URLs of all related entities to the new base/image host, as native's UpdateSourcesRepository.updateSourcesFromApi does via propagateUrlChanges()/propagateImageUrlChanges() (which call updateMangaUrls/updateChapterUrls/updateHistoryUrls/updateNotificationUrls + the *ImageUrls variants, each using replaceBaseUrl()).
- **Root cause:** data/src/commonMain/kotlin/me/manga/yamiapk/data/repository/SourceRegistryRefreshRepositoryImpl.kt:40-46 explicitly documents the omission ('native also propagates a base-URL/image-URL change into the manga/chapter/history/notification tables ... That propagation is intentionally OUT OF SCOPE here'). The upsert at L112-132 only calls sourcesDao.updateBaseUrlAndVersionByName / updateImageBaseUrlAndVersionByName / updateSiteStateByName / deleteSourceByName — no per-entity URL rewrite. Confirmed by grep: propagateUrlChanges/replaceBaseUrl/updateMangaUrls exist ONLY under native-app/. Native ground truth: native-app/.../repo_settings/domain/UpdateSourcesRepository.kt:171-481 (propagateUrlChanges fires BEFORE the registry UPDATE when apiSource.baseVersion > currentVersion, rewriting manga/chapter/history/notification URLs through replaceBaseUrl).
- **Key files:** `data/src/commonMain/kotlin/me/manga/yamiapk/data/repository/SourceRegistryRefreshRepositoryImpl.kt:40`; `data/src/commonMain/kotlin/me/manga/yamiapk/data/repository/SourceRegistryRefreshRepositoryImpl.kt:112`; `native-app/app/src/main/java/me/manga/yami/presentation/features/repo_settings/domain/UpdateSourcesRepository.kt:171`; `native-app/app/src/main/java/me/manga/yami/presentation/features/repo_settings/domain/UpdateSourcesRepository.kt:238`; `shared/src/commonMain/kotlin/me/manga/yamiapk/sources_repositry/common/BaseManga.kt:55`
- **Native (ground truth):** Native rewrites all stored per-entity URLs on a base/image-version bump (UpdateSourcesRepository.propagateUrlChanges/propagateImageUrlChanges), so a library/history item survives a source domain migration. KMP leaves them stale -> the item silently fails to open after the source moves domains.
- **Recommended fix:** Restore native's propagation in SourceRegistryRefreshRepositoryImpl.upsert(): when src.baseVersion > currentBase, before/after the registry UPDATE, rewrite stored URLs for that api across the manga/chapter/history/notification DAOs using a replaceBaseUrl()-equivalent (swap scheme+host, keep path/query/fragment); likewise for imageUrlVersion. This needs the four extra DAOs injected (MangaDao/ChapterDao/HistoryDao/NotificationDao) plus per-api URL update queries (native used in-memory copy+update loops). Keep each rewrite in its own try/catch so one bad row can't abort the rest (native posture).
- **Fix risk:** Medium. Adds writes across 4 tables on a version bump; must scope strictly to rows of the affected api and only when the host actually changes (replaceBaseUrl returns same string otherwise) to avoid needless Room writes. Idempotent by construction (re-running with the same base URL is a no-op). Only fires on the rare baseVersion bump, so steady-state cost is zero.
